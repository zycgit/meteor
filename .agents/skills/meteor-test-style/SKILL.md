# Meteor 测试编写与整理

让测试同时说明“用户怎样使用能力”和“行为是否正确”。遵循仓库 [AGENTS.md](../../../AGENTS.md)，测试应适应内核设计，不为测试增加生产接口、放宽可见性或扭曲职责。

## 先确定测试边界

1. 阅读待测能力的正式入口和实际调用链，再检查同领域已有用例。区分纯算法、存储契约、扩展生命周期和真实 RPC，按所验证的层级选择入口。
2. 单元测试与被测生产类同包，主攻分支、边界和错误路径的覆盖率；可直接测试算法、模型、编解码及 SPI 契约，不必启动完整应用。覆盖率用于寻找遗漏，不为数字增加无意义断言。
3. `net.hasor.realmeteor` 放场景测试，主攻最终用户可以执行的用法。通过 `MetConfiguration` 等公开入口构建和启动上下文，再发布、订阅及调用服务；不直接创建内部 Caller、Dispatcher、Codec 或 Session 来冒充场景。协议互通可使用官方客户端/服务端作为对端，Meteor 一侧仍走正式入口。
4. 单元测试和必要的单协议基础功能测试归属被测实现所在模块。官方 SDK 互通、多语言、多个协议共存以及注册中心与协议组合测试统一归入 `meteor-test`，对端源码、脚本和专用资源随场景迁移；插件不依赖测试宿主或示例工程。`met-example` 只提供用户示例，`meteor-test` 独立持有测试模型、契约、启动入口和 SDK 运行图。两者互不依赖，也不通过生成脚本、资源路径或 Docker 构建复用。允许相同业务代码与契约分别存在于两个工程，重复清理限定在各自边界内。
5. 单元测试保持真实生产包名，不增设 `unit` 层；例如内核连接器测试使用 `net.hasor.meteor.connector`，gRPC 编解码测试使用 `net.hasor.meteor.protocol.grpc.codec`。场景使用 `net.hasor.realmeteor` 根包，再按协议或主题细分；统一业务示例使用 `net.hasor.example`。在 `meteor-test` 中，全部语言业务代码位于 `peer/<语言>`。Java 应用、JUnit 场景与同包单测归 `peer/java/meteor` 的标准 `src/main/java`、`src/test/java`，SDK 对端按实现归 `peer/java/<SDK 名称>`，不兼容版本归其显式版本子目录；公共契约归 `peer/java/contracts`，各自保持独立编译域；不把 SDK 冲突依赖混入 Meteor 运行图。根 `src/main/java/net/hasor/meteor/test/nxn` 负责 Java 编排、调度与报告，`src/main/c` 保存 Linux 原生进程执行器。框架单测归根 `src/test/java`，测试专用代码不进入生产产物。
6. 批量整理时列出范围内每个测试类和方法，逐个标注所属层次、场景及去向。迁移、拆分或合并后核对原有覆盖，不能只改目录名。

测试工程内跨协议共享的公共接口、DTO 和生成绑定由 `meteor-test/peer/java/contracts/src/main/java/net/hasor/example` 持有，Meteor 业务实现归 `peer/java/meteor/src/main/java`，源契约按语法归 `meteor-test/resource/protocol/{proto,thrift,x,wsdl,xsd}`，共享数据与证书分别归 `resource/data`、`resource/certs`，所有语言对端归 `meteor-test/peer`。各语言按这些测试自有契约生成绑定，SDK 依赖由测试构建自行声明。用户示例独立留在 `met-example`，不作为测试输入。单个模块专用的小型测试业务模型留在该模块 `src/test/java/net/hasor/example`。故障对端、同步工具及断言辅助放在使用范围内的测试包或其 `support` 子包，不能伪装成用户示例。单测直接访问同包实现；迁移后删除多余的薄访问适配器。只有测试另一个包的稳定契约确需包内构造时，才保留无断言、无 `@Test` 的最小测试访问适配器；不得为测试修改生产 API 或可见性、复制实现或反射读取私有状态。

## 一个方法只验证一个场景

1. 每个 `@Test` 方法只包含一组明确的前置条件、一个行为目标及其结果。一个场景可以有多个断言，例如错误类型、错误码和资源释放共同证明一次失败的结果；不要求一个方法只有一个 assert。
2. 普通调用与流式调用、请求流与响应流、成功与超时、取消与关闭、不同失败原因等独立场景，必须拆成不同 `@Test` 方法。不要用一个大方法、循环、布尔开关或大 helper 串行执行多个场景。
3. 对协议矩阵，分别命名方向、编码、调用模式或错误条件。外部官方套件也用独立测试方法选择各场景，失败报告须直接指出哪一场景失败。
4. 循环可以生成一个场景所需的负载或枚举同一结果的数据，如并发请求、批次顺序、描述字段列表；不能把不同成功/失败行为藏进循环。失败后的再次调用只有在验证“失败不污染后续调用”这一目标时才属于同一场景。
5. 公共方法只提取业务数据、无资源配置、报文编码或外部对端准备；关键的启动、发布、调用和断言应在场景中可见。不能把旧大测试改为 helper 再由几个新方法重复调用。

矩阵按 `self`（Meteor 两端）、`provider`（Meteor 提供者）、`consumer`（Meteor 消费者）记录方向，并明确语言、协议版本、传输、编码、发现方式和类型层级。直连、Meteor 自动发现、适配发现和外部 SDK 原生发现分别标明；测试器先查地址再传给对端属于适配发现。未编写、未执行、环境缺失或当前实现缺口记为待补齐或未验证，不能改记为不适用或通过。元数据清单不承载任意脚本和测试断言，不发展成另一套测试 DSL。

## 正式入口与测试依赖

1. 注册中心的应用接入测试，通过具体 `RegistryConfiguration`、`MetConfiguration.addExtension`、`buildContext` 和 `getExtension` 获取管理或客户端能力，不绕过扩展直接构造内部实现。按场景需要调用 `context.start()`，保留构建与启动的生命周期区别。
2. `meteor-registry` 内无需外部服务的测试优先用内置 `MemoryRegistryConfiguration`。存储契约测试使用正式 `StorageAccess`；管理查询的数据准备可以独立打开存储会话。
3. 故障注入、会话计数和订阅时序观察，可在测试中装饰真实存储。装饰器只负责该测试的观察或故障，不另写一套存储来代替被测链路。
4. 不通过反射读取私有状态来迁就断言。使用行为、公开查询、返回结果和异常验证；测试已有内部纯逻辑时也不必把它改成 public。

调整注册中心测试时，按需阅读 [注册中心示例](references/registry-tests.md)。其他模块采用同样的组织原则，不照搬注册中心的配置与生命周期。

## 资源与场景分段

1. 先准备配置，再在 `try-with-resources` 中创建上下文、会话等需关闭的资源。多资源每项一行，让创建顺序和反向关闭顺序可见；可以沿用多资源声明末尾的 `//` 保留排版。
2. 生命周期尽量留在当前测试中。相同的无资源配置可以提取方法或放入 `@BeforeEach`；不要把每个场景才需要的上下文、服务和管理对象都堆到测试类字段中。
3. 每个测试方法都按实际步骤用空行与中文 `//` 注释分段，说明准备什么条件、触发什么行为、验证什么结果。简单场景可以将操作与断言放在同一段，不机械套用三段模板，也不给每行代码加注释。只有方法开头的一句总述不等于完成了长场景的分段。
4. 注释必须对应当前方法的单一场景。拆分旧用例后，清理仍描述多个行为的总括注释；异步回调、故障对端和较长辅助方法也按职责分段，简单 DTO、getter 和薄转发不必强加注释。
5. 操作与对应断言相邻。一个生命周期里的连续操作只有服务于同一个验证目标时才能留在同一方法；例如取消后验证其他调用仍可用，属于取消隔离场景。
6. 变量在首次使用附近声明。只有后续阶段确实需要共享的值，才在更外层声明。
7. 中途关闭是测试成员退出、资源释放或幂等性时的真实动作，可以保留在 `try` 内；不能为了形式统一而改变关闭时机。

## 复杂表达式的处理

1. 以 **IDEA 格式化之后** 的结果审视超过 120 字符的代码行；120 字符是复杂度审查线，不是通过机械换行完成的指标。已有多行表达式若会被格式化重新合并，也必须检查。
2. 复杂条件、嵌套取值、长参数列表和断言中的复杂实际值，优先提炼有业务含义的局部变量。变量放在使用处附近，不用 `value1`、`value2` 等占位名字，也不为一个简单取值制造多层中转。
3. 长链式调用在后续调用的 `.` 前分行，并在前一行末尾添加 `//` 或有意义的尾注释，保留 IDEA 格式化后的换行。按配置、发布、调用等语义步骤排版，不只拆在 `=` 后或将每个简单参数强行各占一行；短而清晰的链式调用可以保持单行。
4. 多分支或嵌套三元表达式改成普通 `if`，复杂 lambda 展开为代码块。只为多处复用且职责明确的逻辑提取辅助方法，不把关键操作藏在通用 helper 中。
5. 提取变量不能改变求值时机：`assertThrows` 的被测动作仍在回调内，异步轮询的取值和条件仍在每次回调中计算，不能提前执行或捕获旧状态。
6. Java 控制语句保留完整花括号，成员字段用 `this`，类通过 import 引入。工具选择和字符串比较遵循 `AGENTS.md`；使用现有测试框架，不顺便更换依赖。

## 覆盖与异步验证

1. 围绕行为补齐必要的正常、边界、失败和生命周期场景。范围隔离类操作同时检查目标发生变化、无关服务或实例不受影响。
2. 验证异步结果时用有界 `Future.get` 或等待可观察条件；并发交错用明确的协调手段。固定休眠只适用于确实需要观察“这段时间内没有事件”等场景，不能代替完成信号。
3. 观察自动订阅生效的用例不要改成主动拉取后断言，两者验证的链路不同。真实 RPC 测试必须确实走网络，不能被本地调用捷径替代。
4. 异常用例检查调用方能感知的错误，必要时检查原始原因；不能将缺表、权限、连接等故障一律当成超时成功处理。
5. 保留关闭、取消、订阅停止和失败恢复等已有行为约束。用例难写时先核对生产契约，不通过削弱断言、增加无关重试或跳过用例让测试变绿。

## 验证与交付

1. 单元测试使用所属模块现有 Gradle 任务；`meteor-test` 交叉场景通过 `:meteor-test:dockerTest` 进入 Compose 编排，使用 `--tests` 选择类或方法，任务定义与参数见 [README.md](../../../meteor-test/README.md)。完整测试的 Java 框架、应用、JUnit 与 SDK 构建均在容器中执行；宿主仅需 JDK 17、Docker 与 Compose，不依赖 Python。`peer/python` 协议对端和容器内工具链保留自己的语言环境。先运行受影响用例，涉及共享准备逻辑、生命周期或批量整理时再运行对应模块完整测试；成功后不无故重复运行。
2. 按文件清单逐类、逐测试方法检查分段、表达式和辅助代码，记录无需修改的简单类，不能只处理搜索出的长行。核对差异仍在授权范围、没有漏掉原有断言与边界；测试数量不能代替语义检查。
3. 交付说明整理了哪些场景、补了什么覆盖、实际运行的命令及结果。区分内存存储、真实 RPC 和外部数据库／注册中心验证；如有失败或跳过，明确原因，不混作全部通过。
4. 检查包名与目录一致、单测与被测类同包、场景归属 `net.hasor.realmeteor`、示例归属 `net.hasor.example`、没有遗留重复用例、没有场景绕过公开入口、没有测试辅助类进入主产物。检查测试与 `met-example` 之间不存在项目依赖、源码或资源路径引用、生成输入、启动入口或 Docker COPY 关联。检查迁包后的 SPI 资源和文档命令引用。单元覆盖率与场景互通结果分开报告；拆分增加的用例数不等于新增能力。
5. 若本机可以运行 IDEA formatter，使用项目实际代码风格在本次文件或临时副本上格式化，再复查超过 120 字符的代码；不要修改用户的格式化配置来消除长行。无法实际运行时说明限制，不将手工折行检查称为 IDEA 格式化验收。
6. 源码迁移完成、定向通过和完整全绿验收分别报告。环境问题有独立证据时仍保留失败结果，先处理环境条件，不通过放宽断言、追加业务重试或拼接不同轮次的结果宣布全绿。汇总报告须隔离每次执行产物，并验证测试启动前、后的故障都不会拾取旧 XML。
7. 常驻语言容器由外层 Compose 统一启停，JUnit 只拥有本场景进程。并发场景使用独立端口、临时目录、用户缓存和注册数据；取消时清理本场景进程树，不能删除共享容器或终止其他场景。容器退出、程序退出和 exec 连接中断分别记录，清理失败不能当成通过。默认 16 表示并发场景数，不是 16 套容器。
8. 官方 SDK 互通保持原厂源码和发布制品内容不变；允许正常公开配置，以及官方支持或经 SDK 自体验证可用的依赖组合，并记录实际运行图。兼容修复由 Meteor 一侧承担，不得通过对端改包、改写报文、monkey patch 或隐藏重试掩盖不兼容。测试使用公开 API 与官方生成契约；不可用组合保留失败证据并说明限制。

协议测试的组织与场景范例见 [协议测试](references/protocol-tests.md)。Nacos 的单测、场景与示例可作参考，但已有案例也要服从“一方法一场景”，不照搬其中组合过大的方法。

例如，注册中心模块的完整测试命令是：

```bash
./gradlew :meteor-registry:test --console=plain
```
