# Meteor 分包与命名审查

让包结构表达稳定职责，让类名直接说明对象、阶段和方向。遵循仓库
[AGENTS.md](../../../AGENTS.md)；已有明确的模块边界、包名前缀和用户限定范围优先于本技能。

## 固定审查范围

1. 先确认用户指定的模块、根包和是否允许修改代码。分析任务只给出证据和方案，不提前迁包或改名。
2. 检查工作区状态，保留其他会话及用户的改动。批量迁移前记录范围内的文件、引用和 SPI 资源，不能用还原、清理或格式化覆盖无关改动。
3. 读取范围内的入口、实现、调用者、实现者、测试、`package-info.java` 和资源注册。不能只凭目录名或类名判断职责。
4. 以实际创建关系、对象所有权、生命周期、调用方向和数据流为证据。接口声明只能说明契约，不能代替运行链路。

## 建立结构基线

改动前整理一份简明清单：

- 每个包的公开入口、扩展 SPI、组装类和内部实现。
- 每个类型由谁创建、谁持有、谁关闭，以及主要调用者。
- 包之间的源码引用方向；测试引用单独统计，不用测试依赖推导生产架构。`meteor-test` 与 `met-example` 互不依赖，模型、契约、入口和 SDK 构建各自持有；内容相似不构成跨工程合并理由。
- `META-INF/services`、`module-info.java` 中的 SPI 声明，以及反射、序列化、配置、注解、生成元数据、文档和示例中的完整类名。
- 存在歧义的名称、跨包反向依赖、同职责重复类型和仅为测试公开的成员。

必要时用表格列出 `当前类型 -> 实际职责 -> 建议位置 -> 建议名称 -> 可见性 -> 依据`。先确定目标依赖图和迁移映射，再编辑文件。

## 分包原则

1. 按稳定业务职责和生命周期分包，不按本次改造步骤、文件数量或宽泛后缀分包。
2. 根包保存该领域的公开契约、入口和组装。实现子包保存内聚的具体能力。Java 根包与子包没有天然可见性关系，不能依赖目录层级制造边界。
3. 依赖保持单向。组装层可以依赖具体能力；具体能力不能反向依赖组装层。平级实现避免互相依赖，确实共享的最小契约下沉到双方都能单向依赖的位置。
4. 一个子包应形成能独立说明的职责集合。不要为单个内部类机械建包，也不要把协议、版本、传输、模型和组装全部平铺在一个包中。
5. 纵向能力优先放在自身包内。例如某协议的通道、编解码和处理器放在该协议包中；跨协议选择与端点组装放在更高层。
6. 只有无状态、无所有权、无生命周期的通用数据或契约才进入共享包。承担业务编排、缓存、同步或状态维护的类型应保留为明确的领域服务。
7. `internal`、`support`、`common`、`utils` 不能作为暂存区。无法用一句稳定职责解释一个包时，继续拆解或归位其中类型。
8. 减少类型数量不是最高目标。没有独立状态、并发边界、资源所有权或扩展契约的薄包装可以并入所有者；具有这些边界的类型应保留。
9. 扩展插件持有自身的协议或存储实现及测试。内核只保留稳定扩展契约，不能为单个插件把专属模型带入基础包。

## 命名审查

逐类沿创建、使用、关闭三条链路回答以下问题：

1. 名称中的主体是什么对象或能力？
2. 它处于启动计划、运行路由、协议会话、网络传输还是业务调用的哪个阶段？
3. 它处理入站、出站、客户端、服务端或共享方向中的哪一种？
4. 它真正承担创建、组装、选择、保存状态、处理事件还是转换数据中的哪一种职责？
5. 同一前缀下的所有类型是否属于同一模块；同一后缀是否表达相同语义？

名称按“能力或协议 + 版本 + 方向或角色 + 稳定职责”组合，只保留能消除歧义的部分。例如存在版本差异时使用 `Http1ClientChannel`；没有版本差异时不补版本号。

前缀和后缀使用 `AGENTS.md` 已确定的词汇表，不在本技能中复制另一套定义。对于尚未覆盖的名称，先依据实际职责确认语义；形成新的稳定命名约定时，同步更新 `AGENTS.md`，避免只在一次改造中临时约定。

避免 `Support`、`Common`、`Helper`、`Runtime`、`Adapter`、`Object` 等不能说明职责的名称。它们只有在领域内具有明确且一致的既有含义时才保留。两个类型都带有 `Session`、`Context`、`Manager` 等词时，必须确认它们是否属于同一抽象层；若不是，用 `View`、`State`、`Dispatcher`、`Coordinator` 等真实职责消除误解。

重命名不是文本美化。名称变化必须与职责、包位置和依赖方向一致；如果一个准确名称显得过长，先检查类型是否承担了多项职责。

## 可见性与公共 API

1. 区分 Java `public` 可见性和受支持公共 API。用户 API、扩展 SPI 与跨包稳定契约可以公开；因 Java 子包隔离而必须公开的内部协作类型应保持最小表面，并明确它不是用户入口。实现类、组装细节和状态载体优先使用包内可见。
2. 子类扩展点使用 `protected`，普通内部协作不使用 `protected` 绕过包边界。
3. 不为测试放宽生产可见性。单元测试直接使用被测生产包名；场景测试放在 `net.hasor.realmeteor`，业务示例放在 `net.hasor.example`。迁包后删除多余访问适配器，跨包必要例外遵循测试技能。
4. 接口方法遵循 `AGENTS.md`，默认使用抽象声明。迁包时不能用 `default` 实现掩盖未完成的适配。
5. 迁移公开类型前检查下游模块、SPI、配置和示例；不能把“仓库内已编译”当作没有兼容影响。

## 实施顺序

1. 给出目标包树、包依赖方向和重命名表；说明保留、合并、拆分或迁移的理由。
2. 从最底层契约和共享模型开始，随后迁移具体实现，最后调整组装入口。每一批都保持依赖方向可解释。
3. 同步修改 import、包声明、已有 `package-info.java`、SPI 文件、反射名称、序列化标识、配置、测试、示例和文档。包职责消失时删除对应的 `package-info.java`；不为形式统一强制每个包新建它。使用 `rg` 检查旧完整类名和旧包名残留。
4. 对 SPI 逐项检查 `META-INF/services`、`module-info.java` 的 `uses/provides`、Provider 可见性和构造契约；检查最终构建产物中的服务描述文件，并在已有入口上执行 `ServiceLoader` 冒烟验证。对反射入口检查 `Class.forName`、构造器获取、配置、注解、序列化及生成元数据中的类名。
5. 删除空包、重复桥接层和已经失去调用者的类型。删除前检查反射、SPI 和资源加载，不能仅以 Java 引用为依据。
6. 检查改动后的每个包是否能用一句话说明职责，同前缀类是否完整归属，同后缀是否一致，生产依赖是否仍然单向。

## 验证与交付

先运行受影响模块的编译和定向测试；迁包涉及共享 SPI、启动组装或公共契约时，再运行依赖模块测试。本技能以生产结构为主，测试应服从生产设计；测试自身的分包和命名使用 [$meteor-test-style](../meteor-test-style/SKILL.md)。

交付时说明：

- 最终包结构和依赖方向。
- 重要重命名及其职责依据。
- 合并、拆分和可见性变化。
- SPI、配置、示例和文档是否同步。
- 实际执行的验证及未验证范围。

区分违反仓库现行规则、与当前架构事实冲突和建议性改良。不要用移动文件数量代替架构结论，也不要把编译通过描述为运行期协议或真实服务验证。
