# 按功能与意图编写 Git 提交说明

让读者先知道这次改变解决了什么问题、带来什么行为，再了解必要的实现和兼容影响。提交说明不是文件清单、工作过程记录，也不是把整个开发会话压缩成一条日志。

## 确定记录对象

- 检查仓库规则、分支、工作区状态和近期提交风格。先区分用户要的是说明草稿、修改已有提交消息，还是创建新提交；不要把三者混为一件事。
- 处理提交范围时，固定起止 SHA，明确是否包含起始提交，列出提交顺序和父关系。用户说“从 A 到 HEAD”时结合上下文核实，不能直接套用排除 A 的 `A..HEAD` 而漏掉需要重写的第一条。
- 已有提交以它相对父提交的 diff 为证据，读取文件也使用该提交版本。暂存区、工作区、后续提交中的能力不属于这条提交，即使它们在同一个会话完成。
- 为暂存改动写说明时，以 `git diff --cached` 为边界；需要上下文时可以读取周围代码，但不能将未暂存行为写成已提交内容。

## 从实现还原意图

先看改动分布，再沿入口、调用链、状态生命周期和失败路径读取关键 diff。对每个重要主题确认：

1. 之前的行为或限制是什么？
2. 修改后，用户、调用方或维护者具体获得什么？
3. 哪些范围、协议、生命周期或兼容条件限制了这个结论？

多个模块的重构，按职责和功能组织要点，不按目录顺序逐个报文件名。大范围提交可以委托只读审查，每个审查固定一个提交或独立模块，汇总时仍按原提交边界落笔。

不要从类名推导未确认的能力。例如定义了配置项不代表执行链会读取它；有测试类不代表测试已经通过；有分页参数也不等于底层消除了全量扫描。对关键结论找到实际调用或实现依据。

## 写成读者能判断价值的说明

- 沿用仓库已有语言和标题格式。本仓库使用中文描述配合 `type(scope): 标题`；类型按主要目的选择，不因改了大量文件就一律写 `refactor`。
- 标题说最重要的功能或行为变化。正文补充独立的重要变化、必要原因和限制，不重复标题，不把每个辅助方法都升级为一项功能。
- 提交消息正文必须使用 `1.`、`2.`、`3.` 依次递增的数字编号，不能使用 `-`、`*`、`+` 等无序列表标记；单项正文也从 `1.` 开始，条数服从实际改动。
- 用具体动词和对象：支持、拒绝、保留、隔离、恢复、按范围查询。避免单独写“优化逻辑”“完善功能”“整理代码”。
- 实现名称只在它说明公共契约、入口、兼容影响或关键机制时出现。普通类拆分、方法移动和包迁移，说明其服务的职责或阅读目标即可。
- 使用“新增”前检查父提交；原本已有的能力只是补齐边界，应写“补齐”“修正”或“完善”。只描述最终落盘实现，不复述尝试过又撤回的方案。
- 确认公共 API、配置或数据布局不兼容时，说明受影响对象和适配要求。本仓库可使用 `!` 与 `BREAKING CHANGE:`；不能仅因内部重构就宣称不兼容，也不能编造迁移工具或自动兼容能力。
- 测试改造围绕行为、可阅读性、真实入口及故障定位说明；移动文件数和拆分后的方法数不等同于新增覆盖。已知覆盖减少时不能写“完整保留全部覆盖”。

例如：

```text
不佳：新增应用目录类，修改存储查询，调整测试包。
较好：应用目录独立持久化，列表查询不再扫描全部实例聚合；补充应用离线后的目录查询测试。

不佳：优化线程池逻辑。
较好：让服务独立线程池配置参与实际调度，避免共享业务队列阻塞独立服务。
```

正文长短服从实际改动。简单修复一两句即可；混合大提交保留主要功能和有实际影响的边界，不为了统一条数塞入次要事项。

## 区分证据和验证结果

- 只读 diff 能支持“新增实现”“补充测试”，不能支持“验证通过”。
- 只有结果能对应当前代码版本和执行范围时，才写测试通过；区分单元、嵌入式服务、外部真实服务及性能测试。
- 旧会话、旧报告和记忆可以用于定位线索，不能直接复制为本提交的验收结果。失败后定向通过，也不能合并为整套测试通过。
- 只修改提交消息无需重跑业务测试；应验证提交内容未变。需要额外测试时，根据实际代码变更决定，而不是为了给日志添加数字。

## 获授权后写回 Git

只要求写说明时输出草稿；用户已经明确要求写回提交时，完成检查后直接执行，不重复索要同一授权。授权修改消息不包含合并、拆分提交、推送远端或提交其他工作区内容。

重写前记录原 HEAD、当前分支及原提交链，并保留本地恢复引用。检查合并提交和签名：保持原父关系，不能把旧签名移到已修改的提交上；需要重新签名但缺少凭据时说明具体限制。

只改消息时，保留各提交的代码树、作者、时间和提交顺序，按新父提交连接后继提交。工作区已有改动时，不直接执行可能夹带暂存内容的 `git commit --amend`，不使用 `reset --hard` 清场；可在隔离环境操作，或只重建提交对象并更新引用。

引用更新应校验旧 HEAD，避免覆盖其他会话的新提交。发现并行工作区修改，保留并区分来源；不能为恢复自己的快照而覆盖它们。重写结束核对：

- 每条新旧提交的 tree 一致，父关系与顺序对应，消息之外的元信息按约定保留。
- 暂存区、工作区及其他分支没有被混入或改写；有并行修改时单独核实差异来源。
- 实际 `git log` 中已经出现新说明，记录新旧 SHA 对应关系及恢复引用。

最终简要报告改写数量、新 HEAD 或主要映射、SKILL 等产物和验证范围。明确区分已写入历史的消息与仍留在工作区的新文档，不宣称未经执行的远端推送或测试结果。
